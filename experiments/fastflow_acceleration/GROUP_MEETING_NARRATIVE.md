# EFRetro 推理加速实验：从 FastFlow 启发到离散编辑步长

## 1. 引言

这次实验改的是**推理阶段**，没有重新训练模型。原始 EFRetro 沿着 `t=0` 到 `t=1` 走约 100 个时间步。每一步都调用一次模型，预测当前分子的插入、替换、删除速率，再随机采样编辑事件。即使这一小步最终没有编辑，模型计算也已经发生。

这样的空步很多：在 200 个反应的基线轨迹诊断中，按时间划分的四段里，“两个子候选都没有编辑事件”的比例为 **86.1%～99.6%**。这启发我们把预计编辑活动较低的几个小时间步合成一个大步，减少模型调用；编辑活动较高时继续走小步。这里的“跨步”是依据当前信息提前决定跨度，并不知道未来的小步是否一定没有编辑。[诊断数据](RESULTS.md)

## 2. FastFlow 给了什么启发？

[FastFlow 论文](https://arxiv.org/html/2602.11105)研究的是图像、视频等任务中的**连续流匹配模型**。它的动机是：生成轨迹需要串行调用大模型来预测速度，但有些相邻时间步对轨迹的修正很小，逐步重新计算速度会浪费时间。直接统一减少步数，又可能损伤难处理区间的生成质量。

论文用前面两次真实的速度预测做**有限差分**，估计速度如何随时间变化；在接下来的若干步用这个估计来近似推进状态，省去中间的模型调用。至于一次跳几步，论文交给**多臂老虎机（bandit）**选择：跳得越多，节省的计算越多；下一次真实模型计算会提供近似误差，作为调整跳步长度的反馈。其核心思路是根据局部变化程度分配计算量。[仓库中的论文 PDF](<../../2026--FastFlow Accelerating The Generative Flow Matching Models with Bandit Inference.pdf>)

## 3. 我们怎样迁移到 EFRetro？

我们方法中，状态是离散的分子 token，演化方式是随机的插入、替换和删除事件。它没有 FastFlow 所用的连续状态速度，没法直接照搬对速度做有限差分的办法，所以我们采用“**按局部编辑活动程度分配模型调用**”这个思路，分三步：

### 第一步：算出当前这条轨迹的总编辑强度

在当前分子状态和时间 `t`，模型对**每个序列位置**给出三个数：插入、替换、删除的**对数速率**。程序对这三个数分别取 `exp`，得到普通速率。速率表示模型认为该位置目前有多容易发生对应编辑；它本身不是“已经编辑了几次”，也不是一个概率。

接着按位置掩码过滤：`PAD` 是补齐序列长度的填充位，三种编辑都不计；开头的 `BOS` 是起始标记，可作为插入锚点，但不能被替换或删除；其他非填充位置计入三种编辑速率。最后将**所有位置经掩码过滤后的速率**加起来。每条正在生成的轨迹在每次模型调用后各算一个 `Λ`，并不是把一个 batch 或 20 个增强输入混在一起求和。

下面是一组**纯演示数字**，表中速率已经过 `exp` 还原，和实验中的实际分子及预测值无关：

| 当前位置 | 插入速率 | 替换速率 | 删除速率 | 计入 `Λ` 的数 |
|---|---:|---:|---:|---:|
| `BOS` | 0.4 | 0.9 | 0.8 | 0.4：只计插入 |
| `C` | 0.6 | 0.3 | 0.2 | 1.1：三项相加 |
| `O` | 0.5 | 0.7 | 0.3 | 1.5：三项相加 |
| `PAD` | — | — | — | 0：全部忽略 |

所以这一步的 `Λ = 0.4 + (0.6+0.3+0.2) + (0.5+0.7+0.3) = 3.0`。它是**当前时间、当前整条序列的总速率**；在其他速率不变时，参与求和的位置越多，总强度就越大。代码中的计算与下式一致，其中 `I` 是该类编辑的位置掩码，计入时为 1、不计入时为 0：[位置掩码](../../edit_flows/sampling/ops.py)、[强度求和](../../edit_flows/sampling/branch_sampler_helpers.py)。

```text
Λ = Σ位置 [λ插入 × I插入 + (λ替换 + λ删除) × I替换/删除]
```

### 第二步：用总强度决定走多远

程序计算强度允许的最大步长 `0.15 / max(Λ, 1e-8)`，再与 cubic 调度器当前允许的步长（最多 `0.04`）及终点剩余时间比较，取最小值：

```text
h = min(cubic 调度器允许的步长（最多 0.04）, 0.15 / max(Λ, 1e-8), 1-t)
```

沿用上表的 `Λ=3`，强度上限是 `0.15/3=0.05`，但 `0.04` 的时间上限更小，所以实际最多走 `0.04`。如果下一次重算得到 `Λ=10`，强度上限就变成 `0.015`，这一步会更短。按 `0.04` 的最大时间步计算，`Λ=3.75` 是强度约束开始比它更紧的分界；调度器或终点限制仍可能把实际步长缩得更小。“强”和“弱”没有额外的人为分档。

`Λh≤0.15` 限制的是**当前预测速率与跨度的乘积**，不是对未来编辑概率或质量误差的保证。距 `t=1` 不超过 `0.001` 时，代码会直接走完剩余时间，这一步可能超过该强度限制。

### 第三步：采样编辑并重新评估

确定 `h` 后，程序仍用各位置自己的速率和 `h` 计算编辑事件的采样概率，生成两个子候选并保留一个；`Λ` 只用于决定步长，不直接指定在哪个位置做哪种编辑。到新时间点后再次调用原模型，重新计算各位置速率、总强度和下一步的 `h`，直到 `t=1`。

这版方法**没有使用 FastFlow 的速度外推或 bandit**：每个保留下来的采样点仍做一次真实模型计算，省时来自更少的采样点。扩大步长会改变随机采样路径，因此最终质量需要用实验检验。另有一项独立的工程优化把两个子候选的选择搬到 GPU；它在 pilot 上与旧实现的预测逐字节相同。

## 4. 实验结果与分析

### 完整 test：主要结果

方法在开发集上冻结后，完整 test 一次处理 **5,007 个反应、100,140 个增强输入**，生成 **901,260 条候选**。最终方案包含编辑强度自适应步长和 GPU 子候选选择；完整 test 的实测结果如下。[实验台账与原始结果](RESULTS.md)

| 方法 / 数据 | 采样时间 | 每条轨迹 NFE：平均 / 中位 / 最大 | Top-1 | Top-3 | Top-10 | Oracle-any | Invalid-at-1 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 冻结方案 · 完整 test（5,007 反应） | **3967.39 秒**（约 66 分 7 秒） | **39.04 / 34 / 222** | **64.170%** | **82.564%** | **89.415%** | **92.251%** | **8.300%** |

采样时间从模型加载和输入分词之后开始，包含产品编码、采样和预测写出，不含评分。`NFE` 是一条轨迹实际调用模型的次数。`Top-k` 是正确产物是否进入汇总、去重、排序后的前 `k` 个建议；`Oracle-any` 是每个反应最多 180 条原始输出里是否曾出现正确产物；`Invalid-at-1` 是每个增强输入**第 1 次独立采样**的分子无效率，不是汇总排序后的 Top-1。Top-k 和 Oracle-any 越高越好，Invalid-at-1 越低越好。

第一次完整 test 因一条长轨迹触及 200 次 NFE 保护上限而中断。我们只将保护上限提高到 500 并重跑完整 test，步长参数没有改变；完成运行中实际最大 NFE 是 **222**。500 是异常终止保护值，不是目标采样步数。

历史完整 test 记录为 **5897.02 秒**，与本次的 **3967.39 秒**相比，实测少用 **1929.64 秒**（约 32 分 10 秒），时间比为 **1.49×**。但历史运行的 checkpoint、候选选择策略均不同，且未记录 GPU 型号；这只能作为两次完整 test 的时间记录，不能视为步长方法的严格加速比。本轮没有同权重、同策略的完整 test Full-100 对照。

### 同条件速度证据与质量验收

在同一模型权重、输入、随机种子和候选生成设置的 dev1000 上，原始 Full-100 用 **1071.01 秒**，最终整套方案用 **822.83 秒**，即 **1.302×**、耗时减少 **23.2%**。这份全量对照还包含 GPU 子候选选择优化。若只看步长改动，在同一 GPU 选择实现下的 200 反应 pilot 中，Full-100 为 **188.31 秒**、hazard 为 **161.75 秒**，即 **1.164×**；目前没有步长单项的全量速度消融。

dev1000 中最终方案的平均 NFE 从 100 降到 **39.24**。NFE 降幅大于墙钟时间降幅，因为同一批次里的长轨迹仍会让模型继续运行。未参与方法选择的 **800 个反应**按预设的点估计预算通过质量验收：Top-1/3/10、Oracle-any、Invalid-at-1 相对基线分别变化 **+0.875、+0.875、−0.750、0、−0.650 个百分点**。这些小幅差异不能说明质量提高；Top-10 差值的 95% 配对 bootstrap 区间为 **−2.25 至 +0.75 个百分点**，仍存在抽样不确定性。

### 三个轨迹案例：调用分布与最终输出

我们从上述未调参的 800 个反应中挑选三个**事后示例**，均取第 1 个增强视图、第 1 次独立采样，用同一 checkpoint、输入和随机种子分别跑 Full-100 与 hazard。两边均使用当前 GPU 子候选选择实现，且六条最终预测都与保存的 dev1000 输出逐条一致。表中的“命中”只看这一条轨迹生成的分子是否与目标一致，**不是反应级 Top-k**。

| dev1000 反应编号（从 0 起） | Full-100：NFE / 保留状态变化 / 单轨迹命中 | Hazard：NFE / 保留状态变化 / 单轨迹命中 | 观察 |
|---|---|---|---|
| 0 | 100 / 4 / 是 | **50 / 4 / 是** | 模型调用减半，最终分子相同且正确 |
| 4 | 100 / 12 / 否 | **57 / 7 / 是** | 采样路径改变，本次 hazard 命中 |
| 5 | 100 / 5 / 是 | **61 / 4 / 否（无效分子）** | 采样路径改变，本次 hazard 退化 |

[打开逐步轨迹图](case_study/trajectories.html)可以看到每次模型调用、时间跨度、编辑总强度和保留状态变化；[压缩的原始轨迹 JSON](case_study/trajectories.json.gz)保留了逐步记录。例如反应 5 的 hazard 轨迹在实际模型调用点观测到的 `Λ` 中位数，从前四分之一时间的 **0.204** 升至最后四分之一时间的 **22.269**；相应地，前段只调用 **7** 次模型，末段调用 **38** 次（Full-100 两段分别为 26 和 24 次）。这个案例仍生成了无效分子，说明按强度分配计算并不保证每个案例都答对。三个案例不能用于估计总体质量；总体指标以上面的完整 test 和未调参 800 反应结果为准。

**结论：**完整 test 已完成全部 5,007 个反应，平均每条轨迹约 39 次模型调用，并取得表中的质量指标。加速的严格归因以同条件 dev/pilot 对照为准：最终整套方案的 dev1000 速度为 1.302×，步长单项目前只有 pilot 的 1.164× 直接证据。
