# EFRetro 推理加速实验（组会汇报版）

## 一句话结论

我们把“每条轨迹固定做约 100 次模型计算”改成了“根据当前编辑活动调整计算步长”。原始 Full-100 与最终候选整套实现的 dev1000 耗时分别是 **1071.01 秒**和 **822.83 秒**，速度比为 **1.30 倍**、耗时减少 **23.2%**；未参与调参的 800 个反应满足预先设定的质量预算。最终候选除了 hazard 自适应步长，还包含一项保持选择结果不变的 GPU 分支选择优化，因此 1.30 倍代表**整套候选实现**相对原始基线的速度，不能全部归因于 hazard 步长。完整 test 上，本轮方法耗时 **3967.39 秒**。此前记录的 test 耗时是 **5897.02 秒**，两者直接相除为 **1.49 倍**，但旧运行还使用了不同模型权重和候选选择策略，所以这项历史对比也不能单独归因于步长改动。

## 1. 我们要解决什么问题？

EFRetro 在推理时反复调用 Transformer 来决定下一步对分子做什么编辑。旧方法大致对每条生成轨迹做 100 次模型计算。某些阶段分子编辑活动很少，模型仍然频繁计算，可能浪费时间。

这项实验借鉴了 FastFlow“把更多计算留给变化大的阶段”的思路。我们没有直接照搬论文针对连续流的速度外推，也没有实现 bandit；我们针对离散分子编辑实现了**按编辑强度调整时间步长**。模型权重不变，改变的是推理时何时向前推进、何时再次计算。

## 2. 我们具体怎么做？

### “编辑活动强弱”怎样量化？

模型的速率输出头先给出原始数值 `z`，前向计算返回 `log(softplus(z))` 形式的对数速率；推理代码取 `exp` 得到普通速率 `λ≈softplus(z)`。因此 `z`、模型返回的对数速率、参与求和的普通速率是三个不同阶段的数。代码随后按当前位置的编辑位置掩码过滤，最后把所有位置和三种操作的普通速率加起来，得到当前轨迹的总编辑强度 `Λ`：[模型输出](../../edit_flows/models/transformer.py)、[强度计算](../../edit_flows/sampling/branch_sampler_helpers.py)。

```text
Λ = Σ位置 [ 插入速率 × 插入位置掩码
          + (替换速率 + 删除速率) × 替换/删除位置掩码 ]
```

代码中普通速率为 `exp(模型输出的 log rate)`；位置掩码按当前分子状态决定，填充位置不计入，替换/删除还排除开头的 BOS 位置。因此，`Λ` 是一个**每单位时间的全序列总速率**，不是人工给反应贴的“简单/困难”标签，也不是单个位点的平均值。

每一步的步长 `h` 按下面的规则取三种上限中最小的一个：

```text
h时间上限 = cubic 调度器在当前时间允许的步长，且最多 0.04
h强度上限 = 0.15 / max(Λ, 1e-8)
h = min(h时间上限, h强度上限, 1 - 当前时间)
```

以下数字只用于演示公式，不是本次实验测得的分位数。例如，若 `Λ=3`，强度上限给出的步长是 `0.15/3=0.05`，但 `0.04` 的时间上限会把它压到至多 `0.04`；若 `Λ=10`，强度上限变成 `0.015`，步长就不能超过 `0.015`（调度器或终点限制还可能让它更小）。程序每一步都根据当前模型输出算出 `Λ`，再按公式决定 `h`；“强/弱”没有另外的人为分档。`Λh≤0.15` 是强度乘步长的上限，不应直接读作“事件概率一定小于 15%”。

有一个终点例外：当距 `t=1` 的剩余时间不超过 `0.001` 时，代码会直接补完这点尾段，以保证轨迹到达终点；这一步不再严格套用 `Λh≤0.15`。除此之外，每次重新计算时仍调用原模型，没有缓存或外推旧输出；但跨更大的时间步会改变采样过程本身，所以质量必须通过实验检查，不能假设输出和 100 步方法完全相同。

实验数据按**反应**计数。每个反应有 20 个增强输入；每个增强输入独立运行 9 条轨迹，每条轨迹每步采出 2 个子候选，再按原规则保留 1 条继续。因此 test 的 5,007 个反应对应 100,140 个增强输入和 901,260 条候选输出。我们先用 200 个反应筛选方法，剩余 800 个反应不参与参数选择；最终完整跑 dev1000，并从同一次输出中单独评价这 800 个反应。方法冻结后才运行一次完整 test，没有用 test 调参。

## 3. 主要实验结果

### 3.1 全量端到端对照：dev1000

两种方法使用同一模型权重、同一批输入、相同随机种子、R/M 设置和评分程序。不过推理实现并不完全相同：最终候选还包含保持选择结果不变的 M=2 GPU 分支选择优化，而原始 Full-100 基线使用 Python/CPU 选择。因此下表是**最终候选整套实现**对原始 Full-100 的端到端比较，不是只改变 hazard 步长的全量消融。

这里的 M=2 指每次从两个子候选中选一个继续。优化只是把原先 Python/CPU 上的选择移到 GPU 上；pilot 中新旧选择得到的预测文件逐字节相同。

| 方法 | 完整采样时间 | 相对速度 | 每条轨迹 NFE：平均 / 中位 / 最大 | Top-1 | Top-3 | Top-10 | Oracle-any | Invalid-at-1 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Full-100 原始基线（Python/CPU 分支选择） | 1071.01 秒 | 1.00× | 100 / 100 / 100 | 61.7% | 80.7% | 88.0% | 90.4% | 8.635% |
| Hazard 自适应步长 + M=2 GPU 分支选择 | 822.83 秒 | **1.302×** | **39.24 / 34 / 185** | 62.4% | 81.4% | 87.3% | 90.5% | 8.015% |

相同数据、权重和生成任务下，最终候选整套实现节省 **248.18 秒**，完整运行耗时降低 **23.2%**。Hazard 调步将平均每条轨迹的模型计算次数从 100 次降到约 39 次；但总时间也受到 GPU 分支选择实现影响，不能仅凭这张全量表把两项改动的省时贡献拆开。另一个原因是一个 batch 中的轨迹需要一起处理，少数走得较慢的轨迹会让该 batch 继续调用模型，所以 NFE 减少也不等于墙钟时间按相同比例减少。

要单独观察 hazard 调步，在同一份 200 反应 pilot、同一 GPU 分支选择实现下，Full-100 用时 **188.31 秒**，Hazard 用时 **161.75 秒**，即 **1.164×**、耗时减少 **14.1%**。两者的 Top-1/3/10 分别为 `58.5/80.5/88.0%` 和 `59.0/80.5/88.5%`，oracle-any 为 `91.5/92.0%`，invalid-at-1 为 `8.650/8.675%`。这是 hazard 调步的 pilot 级直接对比；没有用同一 GPU 选择实现再跑一遍完整 dev1000，因此目前没有 hazard 单项的全量速度数值。

### 3.2 未调参的 800 个反应：候选与基线的差值

本表比较最终候选整套实现与原始 Full-100 基线的输出；GPU 选择优化在 pilot 上已验证不改变选择结果。

| 指标 | 整套候选减原始 Full-100 | 配对 bootstrap 95% 区间 | 怎么读 |
|---|---:|---:|---|
| Top-1 | +0.875 个百分点 | −0.500 至 +2.375 | 点估计略高，区间仍包含 0 |
| Top-3 | +0.875 个百分点 | −0.375 至 +2.250 | 点估计略高，区间仍包含 0 |
| Top-10 | −0.750 个百分点 | −2.250 至 +0.750 | 点估计略低，区间仍包含 0 |
| Oracle-any | 0.000 个百分点 | −1.250 至 +1.250 | 没有变化的点估计，区间包含 0 |
| Invalid-at-1 | −0.650 个百分点 | −1.181 至 −0.125 | 无效率点估计更低，区间低于 0 |

预先约定的质量预算要求 Top-k 和 Oracle-any 相对基线最多下降 1 个百分点、Invalid-at-1 最多上升 0.5 个百分点。800 个保留反应的点估计均满足预算。Top-k 和 Oracle-any 的区间包含 0，表示这批数据不足以说明它们有明确改善或退化；我们不把小幅点估计差异解释成模型质量提升。

### 3.3 完整 test：冻结方法的泛化结果

| 反应数 | 采样时间 | 每条轨迹 NFE：平均 / 中位 / 最大 | Top-1 | Top-3 | Top-10 | Oracle-any | Invalid-at-1 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 5,007 | 3967.39 秒（约 66 分 7 秒） | 39.04 / 34 / 222 | 64.170% | 82.564% | 89.415% | 92.251% | 8.300% |

完整 test 的 NFE 终止保护上限设为 500；这表示超过上限时停止并报错，不表示每条轨迹要计算 500 次。本次实际最大值是 222。首次用 200 上限运行时，有一条轨迹未能在上限内完成；该次运行作废，使用 500 上限后完整完成。test 没有同模型、同候选策略的基线，因此此处只报告耗时和泛化指标，不计算 test 加速比。

### 3.4 为什么历史记录是 5897 秒？

仓库中的历史完整 test 记录为 **5897.02 秒**（约 98 分 17 秒）；本轮冻结方法为 **3967.39 秒**（约 66 分 7 秒）。直接按两次实测时间计算：

- 少用 **1929.64 秒**，约 **32 分 10 秒**；
- 新运行耗时约为旧运行的 **67.3%**，对应观察到 **1.49×** 的时间比。

这说明完整任务的实测时间确实明显下降。但两次运行并非严格的单变量对照：历史运行使用不同 checkpoint（历史 SHA 以 `2dcf037c` 开头，本轮以 `7fe982dc` 开头），候选选择策略也不同，且历史元数据没有记录 GPU 型号。因此，组会中应把 **1.49×** 称为“历史完整 test 的实测时间比”。dev1000 的 **1.30×** 是最终候选整套实现相对原始 Full-100 的全量结果；若要单独衡量 hazard 步长，目前只有 pilot 的 **1.164×** 直接对照，尚无全量消融。

## 4. 表中指标是什么意思？

| 指标 | 通俗解释 |
|---|---|
| 采样时间 | 本轮计时从模型载入和产品分词之后开始，包含批量产品编码、采样和预测文件写出，不含评分。 |
| 相对速度 / 加速倍数 | 基线时间除以新方法时间。`1.30×` 表示新方法完成同一项工作约快 1.30 倍。 |
| NFE | 一条生成轨迹中，模型实际进行前向计算的次数。平均值反映一般轨迹，中位数是排在中间的轨迹，最大值显示最慢轨迹。 |
| Top-1 / Top-3 / Top-10 | 对 20 个增强视图的结果按既有规则合并、去重、排序并规范化分子表示后，正确目标是否出现在前 1、前 3、前 10 个候选中。数字是命中的反应百分比；越高越好。 |
| Oracle-any | 对一个反应的 20 个增强视图、每个视图 9 次采样（最多 180 条输出），只要任何输出中出现正确产物就算命中。它衡量“有没有生成出来”，不衡量排名；越高越好。 |
| Invalid-at-1 | 对每个增强视图，检查 9 次独立采样中**采样序号 1**的结果能否解析为有效分子，再计算无效率。这里的“1”不是合并排序后的 Top-1 候选；越低越好。 |
| 个百分点 | 两个百分比直接相减。例如从 8.65% 降到 8.00%，是下降 0.65 个百分点。 |
| 配对 bootstrap 区间 | 对同一批反应重复抽样 10,000 次，观察质量差值可能落在哪个范围；区间用于说明样本波动，不替代预先设定的质量预算。 |

## 5. 结论

1. 最终候选整套实现（Hazard 自适应步长 + M=2 GPU 分支选择）在 dev1000 对原始 Full-100 达到预定的 **1.20×** 最低加速目标，实测为 **1.302×**；未调参的 800 个反应满足质量预算。Hazard 步长单项在同选择实现的 pilot 对比为 **1.164×**；没有全量单项消融。
2. 完整 test 上冻结方法完成了 5,007 个反应的生成，耗时 3967.39 秒，指标如表所示。历史 5897.02 秒与本轮 test 的直接时间比为 1.49×，但因 checkpoint 和候选策略不同，不能把这个比例全部归因于步长变化。
3. 本次借鉴的是 FastFlow 的“按变化自适应分配计算”思想，落地方法是离散编辑强度驱动的时间步控制；没有实现论文中的 bandit 策略或连续速度外推。
